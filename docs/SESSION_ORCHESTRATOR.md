# Market-session lifecycle (KIW-33)

`SessionOrchestrator` provides durable local paper-session scheduling with an explicit versioned trading calendar and `SessionSchedule`. All timestamps must be aware; market timing is Asia/Kolkata. Calendar dates are explicit, including holidays and special sessions. Default premarket readiness begins 15 minutes before open, observation begins at open, and new entries stop 15 minutes before close.

A long-lived service owns one orchestrator instance. Its authenticated manual RUN/STOP handler calls `control(now=..., action='RUN', operator=...)`; its periodic worker calls `tick(now)`. RUN is session-scoped consent, not a bypass of readiness checks. STOP disables new entries while observation/reconciliation continues. No automatic daily RUN exists.

The paper-only `SessionBackend` contract supplies:

- `health(now)`: aware `as_of` plus strict boolean checks for database, configuration, Groww auth, history, features, models and audit. Missing, stale, future or false readiness blocks entries and revokes RUN.
- `warm(session_id)`: load and validate required history/features/models; return exactly True on completion.
- `observe(event_id, now, entries_allowed=...)`: maintain observations/exits, enforcing the passed entry permission in addition to all existing decision and risk gates.
- `close(session_id, now, policy=...)`: reconcile/cancel/flatten according to policy. Return True only when orders and positions are resolved. FLATTEN_ON_FRESH_QUOTE must never invent a fill; HOLD_FOR_RECONCILIATION remains pending until externally reconciled.
- `report(session_id)`: return a JSON-safe final state/report without secrets.

At session close, no new entries are possible. Unresolved positions keep the session CLOSING. Unfinished previous days are reconciled before any new session, even on holidays. Completed reports persist with the session and are not regenerated on ordinary subsequent ticks.

## Restart and process contract

Session state, consent history, timing and report persist in SQLite. New process instances rewarm and require fresh manual RUN. Config/calendar changes for an existing session fail explicitly. Adapter failures record only exception type, revoke entry consent, and persist ERROR. Unknown calendar dates remain closed.

SQLite serializes ticks and control operations. Backend calls occur under the lock and must have bounded timeouts. Adapters MUST deduplicate side effects by event/session keys: a process crash after an external side effect but before the SQLite commit can replay that operation. Run a single service instance; this is not distributed leadership or exactly-once external execution. Do not call network broker order mutation methods from this paper backend.

## EC2 integration

`session_adapter.py` connects the authenticated existing cash-paper RUN/STOP flow and serialized `IntradayService.run_once` worker to this lifecycle when `KIWIT_SESSION_CONFIG` names a configuration file. API and oneshot workers share a consent epoch derived from the Linux boot ID and release SHA. A reboot or deployment requires a new RUN. The adapter verifies Groww readiness with real read-only quotes, checks database/audit/halt state, and requires 20 same-day observations before entries. Its engine is explicitly the existing deterministic cash observer; it does not claim V2 specialist model readiness.

Copy `config/session-orchestrator.example.json` to a root-managed configuration, populate verified explicit sessions and set the environment path to opt in. The supplied empty calendar deliberately cannot start a session. The timer now ticks daily from 09:00 through 16:59 IST; the explicit calendar controls lifecycle eligibility. Existing legacy backend windows can further restrict entries/exits. Configuration is absent by default, preserving the current deployed strategy selection. Configuring this adapter does not replace a Bank Nifty desk or activate V2 inference.

The adapter uses existing transactional/idempotent paper signals and exits, and blocks direct manual signal approval unless lifecycle consent and readiness are valid. Final state is stored in the lifecycle SQLite report. No emails or live orders are generated by the adapter. The V2 in-memory decision core still needs durable recovery before it can be substituted as a backend.

Tests cover manual control, readiness failures, adapter routing, permission revocation on failure, restart rearming, entry cutoff, EOD completion, holiday reconciliation and immutable configuration. Real-market operation remains unvalidated.
